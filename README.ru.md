# valio.code

**Сначала увидеть, как устроена кодовая база, и только потом её менять.**
`valio.code` помогает разработчикам и программным агентам исследовать проект,
находить код за вопросом, понимать доступную информацию о типах и связывать
каждый ответ с конкретной версией исходников.

Цель продукта — граф программной информации: репозитории, проекты, исходный
код, символы и их связи становятся полезным контекстом для разработки, review,
разбора инцидентов и автоматизации.

`valio.code` распространяется по AGPL-3.0. В нём уже есть работающая локальная
основа и есть более широкая roadmap. Эти состояния ниже разделены.

## Что можно делать сегодня

### Работать со стабильной версией кода

Проекты состоят из одного или нескольких репозиториев и корней исходного кода.
Каждая публикация создаёт неизменяемое представление, поэтому исследование,
review или задача агента остаются привязаны к той версии, которая дала
результат. Общий репозиторий может входить в несколько проектов без потери
этого контекста.

Нативный агент умеет однократно захватывать репозиторий или следить за его
изменениями. Он сохраняет задания для повторной отправки, сверяет события
файловой системы и собирает сведения Git. Политика захвата исключает значения
конфигурации до сохранения или отправки исходного кода.

### Находить нужный код с проверяемым результатом

Поиск поддерживает точный текст, поиск по подстроке, регулярные выражения и
логический язык запросов с `AND`, `OR` и `NOT`. Результаты ограничены выбранным
проектом и версией и ведут к исходному коду. Это удобно для поиска
идентификатора, проверки миграции, текста ошибки или сужения области изменения
до открытия редактора.

### Смотреть доступную информацию о типах Go

Текущий анализ Go и поиск типов показывают объявления, поля, методы, параметры,
обобщённые ограничения, теги, именованные типы и константы. Модель типов также
готова представлять видимость, модификаторы, атрибуты, перечисления и физическое
устройство типа, когда языковой адаптер может это установить. Неизвестные
значения помечаются как неизвестные, а не угадываются.

Сегодня это частичная поддержка Go, а не семантический анализ всей программы.
Поддержка других языков и разрешение связей между файлами уровня компилятора —
часть roadmap.

### Получать одни и те же знания в веб-интерфейсе, API и у агента

Веб-интерфейс, защищённый HTTP API и MCP используют одни операции приложения.
Сейчас MCP предоставляет `project_list`, `project_get`, `code_search`,
`type_query` и `index_status`. Разработчик может открыть результат в браузере,
а агент — запросить те же сведения о выбранной версии через MCP.

Локальный набор сервисов включает SurrealDB, основу для надёжных фоновых задач,
инструментирование OpenTelemetry и трассировку Jaeger.

## Планируемый слой интеллектуального поиска

Roadmap добавляет поиск и связи, не выдавая сгенерированный текст за источник
истины. Канонический код остаётся свидетельством; расширенный поиск помогает
разработчикам и агентам быстрее прийти к нужному свидетельству.

### RAG, который сохраняет связь с кодом

Планируемый RAG объединяет несколько вариантов:

1. **Гибридный поиск** объединяет проверяемые точные совпадения с лексическим и
   семантическим поиском: редкие идентификаторы остаются легко находимыми, а
   запросы естественным языком получают больше полезных результатов.
2. **Поиск «родитель—потомок»** находит конкретную функцию, метод или
   объявление и при необходимости добавляет только относящийся к нему контекст.
3. **Поиск с поддержкой кратких описаний** использует документацию и
   сгенерированные резюме как подсказку; рядом всегда доступен канонический код.
4. **Поиск по графу и контексту** проходит по выбранным символам и связям в
   рамках фиксированных проекта и версии, а не возвращает весь репозиторий.
5. **Повторное ранжирование со свидетельствами** упорядочивает кандидаты для
   вопроса и сохраняет ссылки на исходный код и его версию.

Это планируемые возможности. Сегодня нет готового построителя контекста RAG,
сервиса эмбеддингов, индекса BM25, векторного поиска или cross-encoder reranker.

### Восемь планируемых представлений для эмбеддингов

Разным вопросам нужны разные представления кодовой базы. Профили ниже дополняют
друг друга: команда сможет измерить, какое сочетание помогает её репозиториям,
а не предполагать, что одна модель подходит для любого запроса.

| Планируемое представление | Польза для разработчика |
|---|---|
| Исходный код | Помогает находить реализацию, сохраняя идентификаторы и синтаксис. |
| Символы и сигнатуры | Упрощает поиск API, типов, методов и сервисов. |
| Локальный контекст | Связывает результат с окружающим модулем или компонентом. |
| Документация | Соотносит язык продукта, комментарии и вопросы разработчика. |
| Архитектура | Помогает ориентироваться в компонентах и их ответственности. |
| История изменений | Связывает текущий код с причиной и последствиями изменения. |
| Ошибки и диагностики | Ускоряет разбор повторяющихся сбоев. |
| API и события | Связывает контракты, интеграции, сообщения и границы системы. |

Многоязычные модели общего назначения, модели для кода, структурные и графовые
представления, а также контрастивные модели могут быть полезны одновременно.
Это будущие входы для совместной оценки, а не взаимоисключающие редакции
продукта.

### Связи, отвечающие на вопросы разработчика

Планируемый граф сгруппирован по вопросам, на которые он отвечает:

- **Что это и где используется?** Синтаксическое дерево (AST), символы, импорты,
  экспорты, ссылки, псевдонимы и внешние ресурсы помогают найти владельца и
  места использования.
- **Из чего состоит тип?** Граф типов и членов связывает классы, структуры,
  поля, свойства, методы и аргументы с их типами, атрибутами и модификаторами.
  Он поможет найти реализации интерфейса и все использования конкретного
  значения перечисления, проверить доступность метода и особенности хранения.
- **Что может затронуть изменение?** Вызовы, поток управления (CFG), поток
  данных (DFG), зависимости и ограниченные межпроцедурные пути помогают оценить
  последствия.
- **Почему эта операция зависит от условия или значения?** Граф зависимостей
  управления (CDG) и граф зависимостей программы (PDG) выделяют относящуюся к
  вопросу цепочку условий и данных. Общее представление свойств кода (CPG)
  связывает синтаксис, управление и зависимости для составных запросов.
- **Где уже решена похожая задача?** Структурное сходство и сходство ролей в
  графе помогут найти похожий алгоритм, обработчик или компонент даже при
  разных именах и формулировках.
- **Как система ведёт себя на границах?** Контракты API, конфигурация, SQL,
  события, развёртывания и внешние сервисы объясняют связь кода с системой.
- **Почему этому изменению можно доверять?** Тесты, документы, ошибки, история
  изменений, владение и сигналы риска дают контекст для review и сопровождения.

Эти семейства графа, включая графы вызовов, CFG/DFG, связи API/SQL/событий и
историческую аналитику, относятся к roadmap. Текущий поиск и поиск типов Go не
заявляют, что уже предоставляют их.

Подробнее: [проектирование поиска](docs/ru/design/retrieval.md),
[графы кода и эмбеддинги](docs/ru/design/code-graphs-and-embeddings.md),
[конфигурация локального агента](docs/ru/design/agent-configuration.md),
[архитектура](docs/ru/contributing/architecture.md) и
[контракт информации о типах](docs/en/reference/type-information.md).

## Польза для разработчиков и агентов

Разработчики получают воспроизводимые результаты: ответ по исходному коду несёт
проект, репозиторий и неизменяемое представление. Так проще делиться результатом
исследования или review и меньше риск перепутать изменившуюся рабочую копию с
версией, которую действительно проверяли.

Агенты получают ограниченный рабочий контекст вместо неразобранной выгрузки
кода. Уже сегодня они могут искать код и смотреть типы через MCP. В будущем они
смогут получать выбранный контекст связей и поиска с указанием происхождения и
неизвестных состояний. Это сделает помощь агента полезнее, не скрывая от
разработчика свидетельства, нужные для проверки предложения.

## Локальный запуск

Для запуска локального набора сервисов достаточно Docker Compose: не нужны
SDK на хосте, сценарий настройки или файл `.env`.

```powershell
docker compose up -d --build --wait
```

Откройте <http://127.0.0.1:8080> и войдите с токеном локальной разработки:

```text
valio-local-development-token-0001
```

Jaeger доступен по адресу <http://127.0.0.1:16686>. База данных Compose
использует пример учётной записи `root` / `valio` внутри сети Compose. Токен и
учётные данные базы предназначены только для локальной разработки.

Go 1.26.8 нужен для запуска нативного агента из исходников. Node.js 26.8.1
нужен только для разработки фронтенда вне Compose. Сначала воспользуйтесь
[руководством по запуску](docs/ru/getting-started/installation.md), затем:

```powershell
go -C src/back-end run ./cmd/valio-agent index --root C:/path/to/repository --server http://127.0.0.1:8080 --repository repo-id
go -C src/back-end run ./cmd/valio-agent watch --root C:/path/to/repository --server http://127.0.0.1:8080 --repository repo-id
go -C src/back-end run ./cmd/valio-mcp serve --server http://127.0.0.1:8080
```

За конфигурацией и эксплуатационными рекомендациями обращайтесь к
[русской документации](docs/ru/README.md) или [английской документации](docs/en/README.md).
